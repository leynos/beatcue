# BeatCue users' guide

BeatCue is a Python package and planned command-line interface (CLI) for
extracting machine-readable timing cues from video files. The design targets
WebVTT metadata cues, BeatCue JSON, and OpenTimelineIO (OTIO) markers for
editorial and automation workflows.

The current repository contains the package skeleton, technical design, and
roadmap. The video-analysis CLI described below is the intended user contract
for implementation work, not a claim that every command is already available.
The v1 target is deterministic analysis of single-scene or single-shot videos.
Semantic annotation, object tracking, and OTIO marker enrichment are planned
post-v1 extensions. ADR 005 records the object-tracking boundary for later
implementation work, but tracking is not available in the current package
skeleton.

## Current package smoke check

Install the development environment from the repository root:

```bash
uv sync --group dev
```

Run the current package smoke check:

```bash
uv run python -c "from beatcue import hello; print(hello())"
```

Expected output:

```text
hello from Python
```

This confirms that the editable package can be imported. It does not perform
video analysis yet.

## Planned library API

The library API will let callers analyse a video without importing the CLI,
Rich rendering, or filesystem-specific command code. Library callers should use
application services and immutable request objects rather than reaching into
adapters directly.

The planned shape is:

```python
from pathlib import Path

from beatcue import analyse_video
from beatcue.domain import AnalysisRequest

request = AnalysisRequest(
    input_path=Path("input.mp4"),
    webvtt_path=Path("cues.vtt"),
    json_path=Path("cues.json"),
    sample_fps=4.0,
)

result = analyse_video(request)

for cue in result.cues:
    print(cue.kind, cue.time.start_seconds, cue.time.end_seconds)
```

The returned analysis result is the canonical representation. Writers derive
WebVTT, BeatCue JSON, and OTIO from that result, so output formats stay
consistent.

## Planned CLI usage

The primary command will be `beatcue analyse`:

```bash
beatcue analyse input.mp4 \
  --out cues.vtt \
  --json-out cues.json \
  --sample-fps 4
```

For automation, use `--json` to keep standard output machine-readable:

```bash
beatcue analyse input.mp4 --json --json-out cues.json --out cues.vtt
```

Human summaries and progress output use Rich and go to standard error. JSON
data goes to standard output or explicit output files.

### Inspecting media

Use `inspect` before analysis when a workflow needs stream metadata or a clear
compatibility check:

```bash
beatcue inspect input.mp4 --json
```

The command will report duration, streams, frame rate, dimensions, time base,
and dependency diagnostics.

### Agent context

Use `agent-context` when a script or agent needs the command surface in a
versioned, parseable form:

```bash
beatcue agent-context
```

The response will include commands, flags, enum values, profiles, output
formats, delivery schemes, and exit codes.

## Output formats

BeatCue writes each output from the same canonical analysis result. BeatCue
JSON and WebVTT are v1 outputs. OTIO is planned as post-v1 editorial
enrichment.

| Format       | Purpose                                                                                                            |
| ------------ | ------------------------------------------------------------------------------------------------------------------ |
| BeatCue JSON | Lossless analysis output with media metadata, cues, feature summaries, diagnostics, configuration, and provenance. |
| WebVTT       | Time-aligned metadata cues for playback, web tooling, and downstream automation.                                   |
| OTIO         | Editorial timeline markers for tools that consume OpenTimelineIO.                                                  |

_Table 1: Planned output formats._

WebVTT payloads use compact JSON:

```vtt
WEBVTT
NOTE Generated by BeatCue

00:00:03.240 --> 00:00:03.320
{"id":"cue_000001","kind":"cut","label":"Hard cut","confidence":0.93}
```

BeatCue JSON keeps richer data such as features, object observations, semantic
annotations, and model provenance. Its planned v1 schema is based on
`msgspec.Struct`, as recorded in
[ADR 003](adr-003-v1-beatcue-json-schema.md). This is a contract for the
future writer implementation; the current repository does not yet provide the
serializer.

## Configuration

Configuration precedence is:

```plaintext
explicit CLI flag > environment variable > profile > config file > default
```

A minimal planned configuration file looks like:

```toml
[analysis]
sample_fps = 4.0
min_cue_duration_s = 0.08
merge_tolerance_s = 0.15
include_series = false

[outputs]
webvtt = true
json = true
otio = false
```

Profiles will store reusable analysis settings without storing secrets:

```bash
beatcue profile save trailer-review --sample-fps 4 --out cues.vtt
beatcue analyse input.mp4 --profile trailer-review
```

## Common workflows

### Generate deterministic cue sheets

Use deterministic analysis when a workflow needs repeatable timing cues without
semantic model dependencies:

```bash
beatcue analyse input.mp4 --out cues.vtt --json-out cues.json
```

This workflow uses colour, motion, audio, and scene features.

## Planned post-v1 workflows

The workflows below are illustrative post-v1 examples. They are not available
in the deterministic v1 command set.

### Planned post-v1: Add semantic annotations

Semantic annotations will attach captions to existing timing cues when a
workflow needs model-backed descriptions:

```bash
beatcue analyse input.mp4 \
  --out cues.vtt \
  --json-out cues.json \
  --caption-model Qwen/Qwen2.5-VL-7B-Instruct
```

Captions will annotate deterministic timing cues. They will not create timing
cues by themselves.

### Planned post-v1: Recover long-running analysis

The `--wait` flag will let a script block until analysis completes:

```bash
beatcue analyse input.mp4 --json-out cues.json --wait
```

If the process is interrupted, the job ledger will let users inspect recent work
once the planned job commands are implemented:

```bash
beatcue jobs list --json
beatcue jobs get job_123 --json
```

### Planned post-v1: Deliver outputs to a file

The `--deliver=file:<path>` option will support explicit delivery targets:

```bash
beatcue analyse input.mp4 --json --deliver=file:analysis-result.json
```

Unsupported delivery schemes will fail with an error that lists accepted schemes
once delivery adapters are implemented.

## Failure behaviour

BeatCue should fail before side effects when required dependencies or inputs
are unavailable. Planned failure behaviour includes:

- missing `ffprobe` or `ffmpeg` produces a structured dependency error;
- unsupported media produces a validation error with command diagnostics;
- no-audio media still emits visual cues and records a diagnostic;
- existing output files are not overwritten unless `--force` is set;
- invalid model output records diagnostics and does not create cues.
